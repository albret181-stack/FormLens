# Обновления FormLens внутри приложения

## Сценарий пользователя

Колокольчик → проверить → скачать обновление внутри приложения → «Сохранить разбор и перезапустить».

Текущий несохранённый разбор записывается в то же локальное хранилище. При ошибке сохранения установка не начинается. Анализ и перенос проекта должны закончиться до установки. Загрузка обновления может выполняться, пока пользователь работает. ZIP загружает штатный Electron autoUpdater/Squirrel.Mac; браузер для обновления не открывается. После подготовки Squirrel может применить обновление и при обычном закрытии приложения.

Первый переход с прежней версии без встроенного установщика и постоянной подписи выполняется вручную. Это однократный переход на подписанную сборку. Веб-предпросмотр, локальные и ad-hoc сборки не предлагают установку.

## Состояние реализации

Код загрузки, установки, сохранения и сборки артефактов подготовлен. Установки двух подписанных версий на реальном Mac ещё не выполнено. До такой проверки автообновление не считать выпущенным или проверенным.

## Подпись и выпуск

macOS требует постоянную подпись приложения для Squirrel.Mac. Старый `codesign --sign -` не заменяет Developer ID. Нужен сертификат **Developer ID Application** и доступ к нотарификации Apple. Приватный сертификат и пароли нельзя коммитить или отправлять в чат.

В Settings → Secrets and variables → Actions репозитория настроить:

- `FORMLENS_CERTIFICATE_P12`: экспорт сертификата с приватным ключом P12 в base64.
- `FORMLENS_CERTIFICATE_PASSWORD`: пароль P12.
- `FORMLENS_SIGN_IDENTITY`: полное имя `Developer ID Application: … (TEAMID)`.
- `APPLE_TEAM_ID`: постоянный идентификатор команды.
- `APPLE_ID`: аккаунт для нотарификации.
- `APPLE_APP_SPECIFIC_PASSWORD`: специальный пароль приложения для notarytool.

Сертификат импортируется в отдельную временную keychain; файл P12 удаляется, keychain удаляется в финальном шаге Actions. Секреты в артефакты приложения не входят. При отсутствии подписи workflow выпуска останавливается.

Сохраняются bundle ID `local.formlens.studio`, имя приложения и адрес локального интерфейса `http://127.0.0.1:4175`. Не менять путь userData, origin и схему проектов в выпуске автообновления без отдельной миграции.

Версия package.json и package-lock.json должна совпадать с тегом `vX.Y.Z`. Сборка создаёт черновик релиза, который после проверки публикуется с четырьмя артефактами:

- `FormLens-X.Y.Z-arm64.dmg` — первичная установка.
- `FormLens-X.Y.Z-arm64.zip` — подписанное и нотарифицированное приложение для Squirrel.
- `FormLens-X.Y.Z-arm64-update.json` — статический feed Squirrel с версией, точным URL ZIP, размером и SHA-256.
- `SHA256SUMS.txt` — контрольные суммы.

Feed указывает на ZIP конкретной версии. Основной процесс разрешает feed только из этого репозитория и версии, сравнивает версии до запуска Squirrel и не допускает повторную загрузку/проверку во время активной операции. `serverType: json` предотвращает повторную установку той же или более старой версии. Системную проверку подписи не отключать. Все обновления подписывать той же постоянной идентичностью; смена сертификата требует отдельной проверки совместимости.

Локальная неподписанная сборка может создавать DMG для разработки, но не создаёт ZIP/feed, которые притворялись бы рабочим автообновлением.

## Обязательная проверка на Mac до публикации

1. Установить подписанную версию N в Applications; создать и сохранить разбор, затем оставить ещё один несохранённым.
2. Подготовить тестовый подписанный выпуск N+1 с тем же bundle ID и подписью; проверить реальный маршрут GitHub → Squirrel на отдельном тестовом канале/репозитории до массового выпуска.
3. Проверить сетевой сбой, повторные нажатия и возврат из фоновой загрузки к работе.
4. Проверить отказ сохранения и запрет установки во время анализа/переноса.
5. Проверить установку, перезапуск, восстановление обоих разборов и отсутствие нового предложения версии N+1.
6. Проверить повреждённый ZIP и другую подпись: установленная версия не должна замениться.
7. Проверить обычный выход с подготовленным обновлением и отказ пользователя от закрытия при несохранённых изменениях.

Node-тесты проверяют состояния и договорённости, а не реальную установку приложения и поведение Gatekeeper.
